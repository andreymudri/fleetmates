### 3.1 SM-O1: tie a session to its process by walking `/proc` parents

Current default: fall back to the `cwd` + `transcript_path` alias heuristic.

Experiment (stand-in, not Claude Code 2.1.282): deckd spawns the fake `claude` in a PTY; the fake's script fires `Stop` 60 times; `$HOME/.claude/settings.json` registers an async command hook, a Node script that walks `/proc/<pid>/stat` from itself up to pid 1 and sends one JSON line to a Unix socket. The fake runs hook commands through `/bin/sh -c`.

Result, three runs of 60 hooks each: 60 of 60 hook processes had deckd's PTY pid (from the `list` op) in their parent chain, every time. The first links were: hook `node` process, then the PTY process (the fake), then deckd. `/bin/sh -c` exec'd the single command, so no shell appeared in between. The first hook of each run saw `FLEETMATES_DECK_PTY=<ptyId>` in its environment, equal to the ptyId deckd returned (later hooks were not checked for it). The fake's process name in `/proc/<pid>/stat` is `node-MainThread`, not `claude`, so a walk that looks for a process named `claude` would miss the stand-in; it finds the PTY pid only because the experiment compared pids.

One real observation: the same experiment's own parent chain, started from a Bash tool call of a running Claude Code session on this machine (version not checked), contained a process named `claude`, then a shell, then the terminal emulator. So for the native binary the name match works, and the walk reaches the terminal.

What a real-session check would add: whether 2.1.282 runs hooks through a shell or directly, whether any wrapper process sits between `claude` and the hook, and whether an async hook still running after `claude` exits is reparented (the walk would then fail).

Chosen default: for `wrapped` and `launched` sessions, use `FLEETMATES_DECK_PTY` from the hook's environment and do not walk. For observed sessions, walk `/proc` parents to the first process named `claude` (or whose `cmdline` names a `claude` script) and use its pid; keep the alias heuristic as the fallback when the walk finds nothing. Close SM-O1 once one real hook's chain is recorded (M1 dogfood).

### 3.2 SM-O6: screen-idle detection

Current default: on for PTY sessions.

Experiment: every committed 2.1.282 frame rendered through `hub/deckd/screen-model.mjs` at the capture size (120x40) and parsed with `parseScreen` from `hub/server/screen/index.mjs`, once whole and once replayed in chunks of 64, 1024 and 4096 bytes, parsing after every chunk.

Result: the final state is right for all 7 frames (`idle` true for `idle-input` and `question-text`, false for the other five, equal to each `.expect.json`). Replayed in 1024- and 4096-byte chunks, no frame reads idle before its end except the two that end idle. In 64-byte chunks, frames that end busy or on a prompt pass through short idle readings: `permission-edit` reads idle in 3 separate single chunks, `question-options` in 4 separate runs of 1 to 3 chunks, `compacting` in 1 chunk, and `question-text` (which ends idle) once mid-frame as well. Frames are recorded from the previous idle point, so the first idle reading in a frame may be that earlier idle screen; the later ones are mid-repaint. `permission-edit` also flips prompt, busy, prompt, busy, prompt near its end.

So "the input box is empty and no spinner runs" is true for a moment while Claude Code repaints. deckd throttles screen events to 4 per second (`SCREEN_THROTTLE_MS = 250` in `hub/deckd/screen-model.mjs`), which makes a single sample less likely to land mid-repaint but does not rule it out. The frames carry no timing, so how often this happens with real output timing is not measured.

Chosen default: keep screen idle on for PTY sessions, but fire `S.ScreenIdle` (state-machines row 30) only after two consecutive screen events read idle with no output between them, or after 500 ms of idle with no output. A `Stop` hook still ends the turn at once.

### 3.3 SM-O12: PTY size when the terminal and the browser differ

Current default: follow the most recent input source (at most one resize per second).

Experiment: deckd with the fake running `resize.json`; one client sends resizes and writes stamped `terminal` (kitty) and `browser` (chromium) in turn; deckd's own size is read with `list` before each step, and the fake logs every SIGWINCH.

Result (deckd's size, times from spawn):

| ms | Step | deckd size before |
|---|---|---|
| 1209 | terminal asks 100x30, nobody has typed | 80x24, applied at once |
| 1210 | browser asks 140x40, nobody has typed | 100x30; deferred by the one-second rule, applied by 2713 (the fake got a SIGWINCH at 2209) |
| 2713 | terminal types | 140x40; back to 100x30 by 4214 (SIGWINCH at 3211) |
| 4214 | browser types | 100x30; 140x40 by 5716 (SIGWINCH at 4214, at once) |
| 5716 | terminal asks 90x20 while the browser owns the size | 140x40, not applied |
| 7218 | terminal types | 140x40; its stored 90x20 by 7419 (SIGWINCH at 7218, at once) |
| 7419 | browser types 200 ms later | 90x20; 140x40 by 8920 (SIGWINCH at 8218) |
| 8920 | end | 140x40 |

The rule works as written: a non-owner's size is stored and applied when it next types; before anyone types every request applies; resizes are at least a second apart and a deferred one applies the latest target. Its cost is visible too: two people alternating keys resize the PTY on every change of owner, up to once a second, and Claude Code repaints each time.

The fake's SIGWINCH log disagreed with deckd from the second resize on: it logged 100x30 at 2209 when deckd had applied 140x40, and each later entry shows the previous size. This is the known fake defect (section 6, tests); deckd's `list` is the reference here.

Chosen default: keep "follow the most recent input source, at most one resize per second" (already built in `hub/deckd/pty-host.mjs`). The other client letterboxes. Revisit if dogfood shows ping-pong repaints; the fix would be a longer hold for the owner, not a different rule.

### 3.4 TEST-O2: hook-to-UI latency split

Current default (proposed in 15-open-questions): flush a session's reorder buffer at once when `Stop`, `PermissionRequest` or `Notification` is the latest event, keep 250 ms otherwise, and keep the 300 ms budget for those events only.

Experiment (stand-in, not Claude Code 2.1.282): the same chain as SM-O1 (deckd PTY, fake `claude`, `/bin/sh -c`, a Node hook registered `async: true` that does nothing but send one line to a Unix socket). "Fired" is the fake's log timestamp taken just before it spawns the hook command; "received" is when the listening socket sees the line end. 60 hooks, 100 ms apart, three runs.

| Run | fire to line, p50 / p95 / max ms | fire to hook process start, p50 | hook start to send, p50 | send to receive, p50 |
|---|---|---|---|---|
| 1 | 30.5 / 32.6 / 34.6 | 5.7 | 24.0 | 0.6 |
| 2 | 30.1 / 33.0 / 35.1 | 5.8 | 23.8 | 0.6 |
| 3 | 30.3 / 32.6 / 36.0 | 5.8 | 23.9 | 0.6 |

Node's own start-up is about 24 of the 30 ms. With a 250 ms reorder window inside a 300 ms budget, the hook leg alone leaves about 17 ms at p95 for ingest, the database write, the WebSocket push and the browser render; none of those exist yet, so their cost is not measured.

What a real-session check would add: Claude Code's own delay between the event and spawning the hook, and whether it spawns hooks through a shell.

Chosen default: adopt the proposed default. Early flush on `Stop`, `PermissionRequest` and `Notification`, 250 ms otherwise, 300 ms budget for the early-flushed events. Measure the web-server leg in M1 against this 30 ms hook leg.

### 3.5 OPS-O2: environment of a systemd user service

Current default: deckd and the web server run `$SHELL -lc 'env -0'` once at start and use that environment for children.

Experiment: variable names only, never values. `systemd-run --user --pipe --quiet --wait` ran `env -0`, then `$SHELL -l -c 'env -0'` and `$SHELL -l -i -c 'env -0'` inside the same kind of transient service, with stdin from `/dev/null` and a 30 s timeout. `systemd-run --user` asked for nothing. `$SHELL` is bash here.

Result:

- The bare service had 184 names and 10 `PATH` entries. `node` and `claude` resolved there, through `/home/you/.local/share/mise/shims`.
- `bash -l -c` added no names and no `PATH` entries: on this machine the login profile adds nothing; the setup lives in `.bashrc`.
- `bash -l -i -c` added 19 names (`ANDROID_AVD_HOME`, `ANDROID_HOME`, `ANDROID_SDK_ROOT`, `BAT_THEME`, `BROWSER`, `CARGO_HOME`, `JAVA_HOME`, `MANPAGER`, `MANROFFOPT`, `__MISE_DIFF`, `__MISE_EXE`, `__MISE_ORIG_PATH`, `__MISE_SESSION`, `MISE_SHELL`, `RUSTUP_HOME`, `RUSTUP_TOOLCHAIN`, `SSH_ASKPASS`, `SUDO_ASKPASS`, `SUDO_EDITOR`) and grew `PATH` to 23 entries. It removed nothing.
- A first attempt that ran `$SHELL -l -c env` from the agent's own shell instead of from a service also showed Claude Code's session variables (`CLAUDECODE`, `CLAUDE_CODE_*`) and terminal variables (`TERM`, `COLORTERM`, `TERM_PROGRAM`): the comparison must be taken inside the service, or it measures the caller.

Chosen default: take the environment with `$SHELL -l -i -c 'env -0'` (interactive as well as login, so `.bashrc` is read), stdin from `/dev/null`, stderr discarded, a 5 s timeout, falling back to the service's own environment on failure. Drop `TERM`, `CLAUDECODE` and every `CLAUDE_CODE_*` name from what children inherit. `doctor` lists the names that differ, never the values. Not tested: zsh and fish, and a machine where the user manager does not already have the mise shims on `PATH`.
